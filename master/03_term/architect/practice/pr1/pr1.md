## Предварительные замечания к проекту

### Цели и рамки проекта

Целью проекта является разработка платформы данных, которая заменяет прямые обращения аналитиков к продуктивным базам микросервисом ценетрализованным аналитическим слоем, снижает время подготовки отчетности и обеспечивает единую, проверяемую версию бизнес-метрик компании. Результатом проекта является работающий MVP платформы, который включает следующие компоненты:

* Слой приема данных
* Lakehouse-хранилище
* Базовые ETL/ELT-пайплайны
* Слой BI-отчетсноти
* Каталог данных
* Механизмы контроля качества и безопасности

### Деловой контекст

По мере роста финтех-компании количество источников данных (микросервисных платежей, CRM, мобильное приложени, внешние курсы через API, тарифы, котировки) увеличиватся быстрее, чем растут возможности аналитиков обрабатывать их вручную. Аналитики в основном занимаются ad-hoc задачами, при этом также затрачивая много времени на поиск нужных источников и данных в них, также актуальна проблематика теневой отчетности, когда каждая команда аналитиков создает отчетность на свой лад без единого стандарта, что мешает принятию качественных управленческих решений.

## Участиники проекта

* Заказчик – head of data (CDO) компании
* Руководитель проекта
* Команда разработки:
  + 2 дата-инженера
  + 1 BI-разработчик
  + 1 DevOps-инженер
* Бизнес-аналитик
* Представитель инфобеза

## Идеи в отношении решения

В качестве ориентира планируется использовать архитектуру, которая применяется во многих финтех компаниях (например Т-Банк, Сбер):

* Lakehouse-архитектура на основе объектоного хранилища
* Слои данных (Medallion Architecture)
* Аналитический MPP движок
* Оркестратор пайплайнов
* Каталог данных
* BI-решение на основе Apache Superset

## Требования к данным

Источники данных: транзакционные базы данных микросервисом (платежи, счета), CRM-системы, мобильные приложения, внешние источники курсов валют и тарифов. Данные хранятся в колоночном формате (Parquet) в объектном хранилище, метаданные и схемы лежат в отдельном каталоге данных (файлы типа .mmd). Срок хранения сырых данных не менее 1 года, аргегированных витрин не менее 5 лет.

## 3.1. Требования к производительности

Для данной системы особо важным моментом является доступность системы с вероятностью 99.999%.

## Требования безопасности

Работа с финансовыми данными пользователей должна быть замаскированы и подчиняться правилу минимума доступов, то есть ограниченное кол-во людей могут видеть данные с персональной информацией пользователей. Работа с подобными данными регулируются Федеральными законами.

## 4. Проектные вопросы

## 4.1. Оценка сложности, масштаба и реализуемости проекта

По составу подсистем проект относится к крупным распределенным платформам данных корпоративного уровня, что в полном объеме выходит за рамки одной итерации разработки. Для обеспечения реализуемости в заданные сроки и бюджет проект ограничивается MVP-областью. Такой масштаб оценивается как реализуемый силами команды из 5 человек за 4 месяца при условии использования готовых open-source компонентов вместо разработки собственных движков хранения и выполнения запросов.
