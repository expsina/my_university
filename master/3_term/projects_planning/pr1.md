# Практическая работа по управлению IT-проектами

## Часть 1: Характеристика проекта и организации

### Цель проекта
Разработка и запуск мобильного приложения «Фитнесмастер» для платформ iOS и Android. Приложение должно предоставлять пользователям индивидуализированные тренировочные планы, напоминания о занятиях, мотивационные сообщения и возможность отслеживания прогресса в фитнес-целях.

### Основные задачи проекта
- Разработка функциональности индивидуализации тренировочных планов
- Реализация системы уведомлений и напоминаний
- Создание модуля мотивационного контента
- Разработка инструментов отслеживания прогресса пользователя
- Обеспечение функционирования на iOS и Android платформах
- Внедрение системы in-app покупок

### Требования и ограничения

Требования:
- Приложение должно быть запущено не позднее 1 декабря 2024 г.
- Бюджет проекта не должен превышать 5 млн. рублей
- Не менее 80% отзывов пользователей должны быть положительными
- Достижение 100 000 загрузок в первые три месяца после запуска
- Кроссплатформенность (iOS и Android)

Ограничения:
- Временное ограничение: июнь 2024 - декабрь 2024 (6 месяцев)
- Финансовое ограничение: 5 млн. рублей
- Ограничение по загрузкам: минимум 100 000 в квартал

### Вопрос 3: Выбор технологий и инструментов разработки

Архитектура приложения:
- Клиентская часть: Native разработка (iOS - Swift, Android - Kotlin) для максимальной производительности и пользовательского опыта
- Альтернатива: Flutter или React Native для более быстрой кроссплатформенной разработки (сэкономит время и ресурсы)
- Серверная часть: Node.js + Express или Python + Django/Flask
- База данных: PostgreSQL (надежность, безопасность) или MongoDB (гибкость схемы)
- API: REST API или GraphQL

Выбранные технологии и обоснование:

Native разработка (Swift/Kotlin):
- Преимущества: максимальная производительность, лучший UX, полный доступ к функциям ОС
- Недостатки: длительность разработки, необходимость двух отдельных команд
- Обоснование: для фитнес-приложения критична производительность, быстрая обработка данных о тренировках

Node.js для backend:
- Преимущества: быстрая разработка, одинаковый язык (JavaScript), асинхронность, хорошо масштабируется
- Обоснование: позволяет ускорить разработку сервера, хорошо подходит для real-time уведомлений

PostgreSQL для БД:
- Преимущества: надежность, безопасность, мощные функции, соответствие ACID
- Обоснование: критично для хранения личных данных о тренировках и профилей пользователей

Firebase/AWS для инфраструктуры:
- Push-уведомления: Firebase Cloud Messaging
- Хранилище файлов: AWS S3 или Firebase Storage
- Обоснование: масштабируемость, надежность, встроенная аналитика

Инструменты разработки:
- IDE: Android Studio (для Android), Xcode (для iOS), VS Code (для backend)
- Версионирование: Git
- Тестирование: JUnit, XCTest, Jest
- Проверка кода: SonarQube, ESLint

### Вопрос 7: План действий при невыполнении ключевых критериев

Сценарий 1: Неполучение 100 000 загрузок за 3 месяца

Вероятная причина:
- Недостаточная видимость в магазинах приложений
- Слабая маркетинговая кампания
- Неконкурентное предложение
- Негативные отзывы в первые недели

План действий (этапы реагирования):

Неделя 1-2 после запуска (при росте менее 5000 загрузок/неделю):
- Срочное совещание team leads и менеджмента
- Анализ причин слабого спроса (аналитика, отзывы, конкурентный анализ)
- Срочная оптимизация ASO (переработка описания, скриншотов, ключевых слов)
- Запуск чрезвычайных мер: контакт с influencers, экстренная реклама

Месяц 1 (при загрузках менее 20 000):
- Пересмотр маркетингового плана
- Увеличение бюджета на рекламу (дополнительно 300k-500k рублей)
- Запуск агрессивной кампании в социальных сетях
- Временное снижение цены или расширение бесплатного функционала
- Запуск партнерских программ с фитнес-центрами

Месяц 2 (при загрузках менее 50 000):
- Комплексный пересмотр стратегии
- Провести пользовательские исследования (why users don't download)
- Возможное улучшение функционала на основе отзывов
- Расширение маркетинговых каналов
- Рассмотрение возможности снижения цены подписки

Месяц 3 (при загрузках менее 70 000):
- Признание того, что целевой показатель не будет достигнут
- Анализ: это временное явление или систематическая проблема?
- Переформулировка целей (например, 70k загрузок + темп роста 5k в месяц)
- Построение плана восстановления на 6+ месяцев

Долгосрочные меры:
- Продолжение регулярных обновлений и улучшений
- Расширение функционала за счет пользовательских пожеланий
- Поиск новых партнеров и каналов дистрибуции
- Возможно, платная интеграция с другими популярными приложениями (здоровье, спорт)
- Локализация на другие языки для привлечения международной аудитории



Сценарий 2: Превышение бюджета (более 5 млн рублей)

Вероятные причины:
- Увеличение команды разработчиков (дополнительные специалисты)
- Задержки в разработке
- Непредвиденные технические трудности
- Расширение scope функциональности

План действий:
- Немедленное уведомление заказчика о перерасходе
- Анализ причин и прогноз окончательной стоимости
- Переоценка приоритетов: какие функции критичны для запуска
- Возможное снижение scope: отложить некритичные функции на версию 1.1
- Оптимизация процессов разработки для снижения издержек
- Поиск дополнительного финансирования (если согласуется с заказчиком)



Сценарий 3: Задержка запуска (позже 1 декабря 2024)

Вероятные причины:
- Обнаружение критических ошибок на позднем этапе
- Проблемы с сертификацией в App Store/Google Play
- Неожиданные технические сложности
- Недостаточное тестирование

План действий:
- Анализ критичности задержки (дни, недели, месяцы?)
- Переговоры с заказчиком о сдвиге deadline
- Интенсификация работы: дополнительные часы, временное расширение команды
- Приоритизация: выпустить MVP с базовым функционалом, остальное в обновлениях
- Рассмотрение параллельного запуска версий (сначала Android, потом iOS или наоборот)
- Компенсация задержки интенсивными маркетинговыми мерами



Сценарий 4: Низкие отзывы (менее 80% положительных)

Вероятные причины:
- Критические ошибки и баги
- Плохой UX/UI дизайн
- Неправильная работа основных функций
- Конкуренция с лучшими приложениями

План действий:
- Срочный анализ отрицательных отзывов (группировать по проблемам)
- Выпуск срочного патча для исправления топ-3 критических проблем
- Запуск программы стимулирования: попросить положительно оценивших пользователей оставить отзывы
- Трансформация отрицательного отзыва: личный ответ с предложением помощи
- Возможное переделывание интерфейса на основе отзывов
- Запуск in-app tutorial для новых пользователей (снизить learning curve)



### Вопрос 8: Меры безопасности и соответствие законодательству

Меры обеспечения безопасности данных:

Шифрование данных:
- Шифрование при передаче: использование HTTPS/TLS 1.2+ для всех соединений
- Шифрование в покое: использование AES-256 для хранения чувствительных данных на сервере
- Локальное шифрование: использование Keychain (iOS) и KeyStore (Android) для хранения токенов аутентификации

Аутентификация и авторизация:
- Двухфакторная аутентификация (опционально)
- OAuth 2.0 для безопасного обмена токенами
- JWT (JSON Web Tokens) для управления сессиями
- Периодическое обновление токенов доступа

Защита от уязвимостей:
- Защита от SQL-инъекций: использование parameterized queries
- Защита от XSS (Cross-Site Scripting): санитизация пользовательского ввода
- Защита от CSRF (Cross-Site Request Forgery): использование CSRF токенов
- Защита от Man-in-the-Middle атак: certificate pinning для мобильного приложения
- Регулярные security code reviews
- Использование OWASP Top 10 как справочника

Управление доступом:
- Принцип наименьших привилегий (Principle of Least Privilege)
- Разделение ролей: пользователь, администратор, суперадминистратор
- Ограничение доступа сотрудников к персональным данным пользователей
- Логирование всех действий администраторов

Тестирование безопасности:
- Регулярные penetration testing (минимум раз в год, перед запуском)
- Статический анализ кода (SonarQube, Checkmarx)
- Динамический анализ (OWASP ZAP, Burp Suite)
- Тестирование на уязвимости мобильного приложения
- Bug bounty программа (после запуска, привлечение этичных хакеров)

Инфраструктурная безопасность:
- Использование Web Application Firewall (WAF)
- DDoS защита
- Регулярные обновления серверного ПО и библиотек
- Мониторинг безопасности 24/7 (SIEM система)
- Резервные копии данных с шифрованием
- Изоляция баз данных в отдельных сетях



Соответствие законодательству о защите персональных данных:

Применимые нормативно-правовые акты:
- Федеральный закон №152-ФЗ "О защите персональных данных" (Россия)
- GDPR (General Data Protection Regulation, если есть пользователи из ЕС)
- Закон о защите прав потребителей (Федеральный закон №2300-1)

Процесс обеспечения соответствия:

Сбор согласия:
- Запросить явное согласие пользователя перед сбором персональных данных
- Создать понятную политику конфиденциальности (размещена в приложении)
- Согласие на обработку персональных данных при регистрации
- Согласие на отправку пуш-уведомлений

Типы собираемых данных и их обработка:
- Имя и email - хранятся зашифрованными, используются для коммуникации
- Пароль - хранится в виде хеша (bcrypt, scrypt)
- История тренировок - хранится в защищенной БД, доступна только пользователю
- Данные о здоровье (вес, пульс) - особо защищенная информация, максимальное шифрование
- IP адрес - логируется для аналитики, удаляется через 30 дней
- Информация об устройстве - используется для совместимости

Права пользователей (GDPR/ФЗ-152):
- Право на доступ: предоставлять выгрузку данных по запросу (в течение 30 дней)
- Право на исправление: возможность изменения профиля
- Право на забывчивость: удаление всех данных при удалении аккаунта (в течение 60 дней)
- Право на ограничение обработки: приостановка использования данных

Политика конфиденциальности:
- Размещение на сайте и в приложении
- Описание всех типов данных, которые собираются
- Цели обработки данных
- Сроки хранения
- Третьи стороны, которые получают доступ
- Контактная информация DPO (Data Protection Officer)

Обработка данных третьими сторонами:
- Договоры обработки данных со всеми поставщиками услуг
- Firebase - прямой договор о конфиденциальности данных
- Платежные системы (Apple, Google) - соответствие PCI-DSS
- Аналитика (Mixpanel, Amplitude) - минимизация передачи ПД

Инцидент-менеджмент:
- Процесс для быстрого обнаружения утечек данных
- Уведомление пользователей в течение 72 часов при утечке (согласно ФЗ-152)
- Уведомление регулятора (Роскомнадзор)
- Проведение расследования
- Меры по предотвращению повтора

Кадровые меры:
- Обучение команды по защите данных (GDPR/ФЗ-152)
- NDA для всех разработчиков и сотрудников поддержки
- Ограничение доступа к персональным данным только необходимым лицам
- Регулярные проверки соответствия политике

Документирование:
- Реестр обработки данных (Register of Processing Activities)
- DPIA (Data Protection Impact Assessment) для критичных обработок
- Журналы доступа к системам
- Регулярные аудиты безопасности

Ответственность:
- Назначить Data Protection Officer (DPO) для управления соответствием
- Регулярные проверки соответствия нормам (quarterly)
- Готовность к проверкам регулятора
- Страхование ответственности за утечку данных
